## 1. Recommended Stack & Rationale

### 1.1 Core Choices

| Layer | Choice | Version |
|---|---|---|
| Framework | Next.js (App Router) | 15.x |
| Language | TypeScript | 5.x |
| Styling | Tailwind CSS | 4.x |
| Animation | Framer Motion | 11.x |
| Data fetching (client) | TanStack Query (React Query) | 5.x |
| Forms | react-hook-form + zod | 7.x / 3.x |
| State (global/minimal) | Zustand | 4.x |
| CMS/DB | Firebase (Firestore + Storage + Auth) | 11.x SDK |
| Hosting | Firebase App Hosting (SSR-native) | GA |

### 1.2 Framework Comparison

| Criterion | Vite SPA | **Next.js 15 App Router** |
|---|---|---|
| Blog / store SEO | Poor — JS-only, crawlers see empty HTML | **Excellent** — RSC renders full HTML at build or request time |
| Static marketing pages | Good | **Excellent** — Static generation (SSG) by default |
| Dynamic routes (blog, store) | Manual SSR workaround needed | **Built-in** — `generateStaticParams` + ISR |
| Streaming / Suspense | Limited | **Native** — React 19 async components |
| Firebase App Hosting | Not officially supported | **First-class** — App Hosting detects Next.js automatically |
| Image optimization | Manual (vite-imagetools) | **Built-in** `next/image` |
| API routes / Server Actions | Separate Express layer needed | **Built-in** — Server Actions + Route Handlers |
| i18n | Plugin | **Built-in** middleware routing |

**Decision: Next.js 15 with App Router.**

Key reasons:
- The blog and store are public-facing content requiring Google-indexable HTML at the page level. Vite SPA would require a separate SSR server or static pre-render pipeline to achieve the same; Next.js provides this out of the box.
- Firebase App Hosting natively supports Next.js (SSR, ISR, Server Actions, edge middleware) without configuration. This keeps the entire stack on Google Cloud, satisfying the "all-Google" constraint.
- The App Router's React Server Components (RSC) pattern means Firestore reads on marketing and blog pages happen server-side with `firebase-admin`, avoiding client-side SDK initialization latency and keeping API keys off the browser.

### 1.3 Why Firebase App Hosting over Vercel/Netlify

Firebase App Hosting (generally available as of 2024) runs Next.js on Cloud Run and is managed via `firebase.json`. It provides preview channels (equivalent to Vercel preview deploys), custom domains, and integrates with Firebase Auth, Firestore, and Storage through the same Google Cloud project. This avoids splitting infra across two providers.

### 3.4 Legacy Duda URL Redirects (301)

Implemented in `src/middleware.ts` using Next.js `NextResponse.redirect`:

```typescript
// src/middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

const LEGACY_REDIRECTS: Record<string, string> = {
  '/read-more':                  '/about',
  '/teams':                      '/team',
  '/category/dance-entertainment': '/productions',
  '/store':                      '/store',   // same path — no redirect needed; included for clarity
};

export function middleware(request: NextRequest) {
  const path = request.nextUrl.pathname;

  if (LEGACY_REDIRECTS[path]) {
    return NextResponse.redirect(
      new URL(LEGACY_REDIRECTS[path], request.url),
      { status: 301 }
    );
  }

  // Admin auth guard (see §4.5)
  if (path.startsWith('/admin') && path !== '/admin/login') {
    const token = request.cookies.get('__session')?.value;
    if (!token) {
      return NextResponse.redirect(new URL('/admin/login', request.url));
    }
  }

  return NextResponse.next();
}

export const config = {
  matcher: [
    '/read-more',
    '/teams',
    '/category/:path*',
    '/admin/:path*',
  ],
};
```

### 4.2 Server vs. Client Components

**Default to Server Components.** Only add `'use client'` when the component needs:
- Browser APIs (scroll, window, localStorage)
- React hooks that require interactivity (useState, useEffect, event handlers)
- Third-party libs that depend on the DOM (Framer Motion animating on user gesture)

| Component | Type | Reason |
|---|---|---|
| `Header` | Client | Scroll-aware transparency; mobile menu toggle |
| `MobileMenu` | Client | Open/close state |
| `HeroSection` | Server (static) + Client overlay | Background video loads client-side; text is server |
| `FeaturedProductions` | Server | Firestore fetch in RSC |
| `BlogList` | Server | Firestore fetch |
| `BlogPost` | Server | Rich text render |
| `EnrollButton` | Client | Firebase Auth check; redirect to checkout |
| `AddToCartButton` | Client | Zustand cart mutation |
| `CartDrawer` | Client | Zustand state; slide animation |
| `ContactForm` | Client | react-hook-form; toast feedback |
| `BookingForm` | Client | react-hook-form; toast feedback |
| `AdminSidebar` | Client | Navigation state |

**Pattern: Async RSC with Suspense boundary**


### 4.3 Forms — react-hook-form + zod

All public forms follow this pattern:

```tsx
// src/components/forms/ContactForm.tsx
'use client';

import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';
import { submitContact } from '@/lib/actions/contact';

const schema = z.object({
  name:    z.string().min(2, 'Name is required'),
  email:   z.string().email('Valid email required'),
  subject: z.string().min(3),
  message: z.string().min(10, 'Message must be at least 10 characters'),
});

type ContactData = z.infer<typeof schema>;

export function ContactForm() {
  const { register, handleSubmit, formState: { errors, isSubmitting } } = useForm<ContactData>({
    resolver: zodResolver(schema),
  });

  const onSubmit = async (data: ContactData) => {
    const result = await submitContact(data);  // Server Action
    // handle result, show toast
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)} noValidate>
      {/* fields */}
    </form>
  );
}
```

The Server Action in `src/lib/actions/contact.ts` validates again server-side (never trust client validation alone) and calls `POST /api/contact`.

### 4.4 State Management

| Concern | Tool | Location |
|---|---|---|
| Server data (blog posts, productions) | React Server Components + `fetch` cache | RSC; no client state |
| Server data on Client Components | TanStack Query | `src/hooks/` wrapping `src/lib/queries/` |
| Cart items | Zustand (persisted to localStorage) | `src/store/cartStore.ts` |
| Auth state | `useFirebaseUser` hook (wraps `onAuthStateChanged`) | `src/hooks/useFirebaseUser.ts` |
| Toast / notifications | Sonner (lightweight) | Root layout via `<Toaster />` |
| Modal / drawer open state | Local `useState` in each component | Co-located |

Avoid Context for data that changes infrequently; use Zustand only for truly global, frequently-mutated state (the cart). Everything else is either RSC or TanStack Query cache.

### 4.5 Admin Auth Guard

The admin section uses Firebase Auth with a session cookie (`__session`). On login, the client exchanges an ID token for a session cookie via a Server Action. The middleware reads `__session` and redirects unauthorized visitors.

```typescript
// src/lib/actions/auth.ts
'use server';

import { adminAuth } from '@/lib/firebase/admin';
import { cookies } from 'next/headers';

export async function createSessionCookie(idToken: string) {
  const expiresIn = 60 * 60 * 24 * 5 * 1000; // 5 days
  const sessionCookie = await adminAuth.createSessionCookie(idToken, { expiresIn });
  cookies().set('__session', sessionCookie, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    maxAge: expiresIn / 1000,
  });
}
```

## 5. Data Fetching & Firebase Integration Seams

### 5.1 Server-Side (firebase-admin)

All server components and API routes use `firebase-admin`. The admin SDK is initialized once as a singleton:

```typescript
// src/lib/firebase/admin.ts
import { getApps, initializeApp, cert, App } from 'firebase-admin/app';
import { getFirestore } from 'firebase-admin/firestore';
import { getAuth } from 'firebase-admin/auth';
import { getStorage } from 'firebase-admin/storage';

const serviceAccount = JSON.parse(process.env.FIREBASE_SERVICE_ACCOUNT_JSON!);

const adminApp: App = getApps().length
  ? getApps()[0]
  : initializeApp({ credential: cert(serviceAccount), storageBucket: process.env.FIREBASE_STORAGE_BUCKET });

export const adminDb   = getFirestore(adminApp);
export const adminAuth = getAuth(adminApp);
export const adminStorage = getStorage(adminApp);
```

**Typed query example** (seam with Back-End agent's Firestore schema):

```typescript
// src/lib/queries/blog.ts
import { adminDb } from '@/lib/firebase/admin';
import { BlogPost } from '@/types/blog';

export async function getBlogPosts(limit = 12): Promise<BlogPost[]> {
  const snap = await adminDb
    .collection('posts')         // collection name from docs/03-backend-schema.md
    .where('status', '==', 'published')
    .orderBy('publishedAt', 'desc')
    .limit(limit)
    .get();

  return snap.docs.map(doc => ({ id: doc.id, ...doc.data() } as BlogPost));
}
```

### 5.2 Client-Side (Firebase Client SDK)

Used only for:
- Firebase Auth (`onAuthStateChanged`, `signInWithEmailAndPassword`, Google OAuth)
- Real-time listeners, if any (e.g., cart sync across tabs — Phase 3+)


**Video (hero, production reels):**

Videos are hosted in Firebase Storage. Use a poster frame (JPEG) loaded via `next/image` for the initial paint, then lazy-load the video with an Intersection Observer:

```tsx
// src/components/home/HeroSection.tsx
'use client';
import { useRef, useEffect } from 'react';
import Image from 'next/image';

export function HeroSection({ videoUrl, posterUrl }: HeroSectionProps) {
  const videoRef = useRef<HTMLVideoElement>(null);

  useEffect(() => {
    const video = videoRef.current;
    if (!video) return;
    const observer = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) {
        video.src = videoUrl;  // only load when visible
        observer.disconnect();
      }
    });
    observer.observe(video);
    return () => observer.disconnect();
  }, [videoUrl]);

  return (
    <section className="relative h-screen overflow-hidden">
      <Image src={posterUrl} alt="Travis Payne" fill className="object-cover" priority />
      <video ref={videoRef} autoPlay muted loop playsInline className="absolute inset-0 w-full h-full object-cover" />
      {/* overlay + headline */}
    </section>
  );
}
```

## 6. Performance, SEO, Accessibility & Analytics

### 6.1 Performance Budget

| Metric | Target | Strategy |
|---|---|---|
| LCP | < 2.5 s | Priority `next/image` on hero; preload hero video poster |
| INP | < 200 ms | Minimal client JS; Zustand over Context; no heavy libs on first paint |
| CLS | < 0.1 | All images have `width`/`height` or `fill` with aspect-ratio container |
| TTFB | < 800 ms | SSG/ISR; Firebase App Hosting on Cloud Run (same region as Firestore) |
| Bundle | < 150 kB JS (first load) | RSC ships zero client JS by default; code-split by route |

- Use `next/font` to self-host fonts (eliminates Google Fonts render-blocking request).
- Tree-shake Framer Motion — import only `motion` and `AnimatePresence`, not the full library.
- Use `dynamic()` with `ssr: false` for heavy admin editor (Tiptap) to keep it out of the public bundle.

### 8.2 Asset Migration Checklist

- [ ] Download all images from Duda (Settings → Site Assets or inspect Network tab)
- [ ] Resize hero images to 1920×1080 max; optimize to WebP with `sharp` or Squoosh
- [ ] Upload all images to `Firebase Storage / assets/`
- [ ] Log each Firebase Storage URL in a migration spreadsheet
- [ ] Map old Duda image URLs to new Firebase Storage URLs (for any hardcoded references)

### 8.3 Staging on Temporary Domain

1. Deploy to Firebase App Hosting preview channel: `firebase hosting:channel:deploy staging`
2. This generates a URL like `https://travispayne-prod--staging.web.app`
3. Share with Travis/stakeholders for content review
4. Validate all 301 redirects with `curl -I https://travispayne-prod--staging.web.app/read-more`
5. Run Lighthouse on staging; confirm Core Web Vitals pass

### 8.4 DNS Cutover

**Current DNS:** Points to Duda's hosting  
**Target:** Firebase App Hosting custom domain

Steps:
1. Add `travispayne.com` as a custom domain in Firebase App Hosting console
2. Firebase provides TXT record for domain ownership verification → add to DNS registrar
3. Firebase provides `A` and `AAAA` records for the apex domain
4. Firebase provides `CNAME` for `www` subdomain
5. **Do not update DNS yet.** Keep Duda live.
6. After staging sign-off, schedule cutover for a low-traffic window (e.g., Tuesday 2 AM PT)
7. Update DNS at registrar; TTL change propagates in 5–30 min (pre-lower TTL to 300 s 24 h before)
8. Verify HTTPS certificate provisioned by Firebase (automatic via Let's Encrypt)
9. Verify `travispayne.com` and `www.travispayne.com` both resolve to new site
10. Keep Duda subscription active for **14 days** as rollback option

**Rollback:** If critical issues discovered, revert DNS `A`/`AAAA` records to Duda IPs (documented before cutover). Propagation: ~5 min with low TTL.

### 8.5 SEO Preservation

- All 301 redirects implemented in `middleware.ts` before DNS cutover (see §3.4)
- Submit updated sitemap to Google Search Console immediately after cutover
- Monitor Google Search Console for crawl errors for 30 days post-cutover
- Verify Google Analytics continuity (GA4 property ID unchanged; just update the measurement ID in env if needed)
